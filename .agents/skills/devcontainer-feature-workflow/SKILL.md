# Dev Container Feature workflow

Use the current Feature's files as the implementation source of truth. Read
[the reference index](../../knowledge/reference-index.md) when a specification,
schema, CLI flag, or Action behavior needs confirmation.

1. Inspect `src/<id>/devcontainer-feature.json`, `src/<id>/install.sh`, and
   `test/<id>/` before editing. For a new Feature, use the same layout and add
   a default test at `test/<id>/test.sh`.
2. Declare user options in the manifest and implement their behavior in the
   installer. Check the Feature spec and schema for option resolution,
   dependencies, and metadata rather than copying a nearby Feature blindly.
   Keep installation safe for the container's remote user and supported base
   images.
3. Cover default behavior in `test.sh`; add a named scenario and matching
   `test/<id>/<scenario>.sh` when options or combinations need testing.
   Use `just test-feature <id>` locally. Run `just test-global` if a shared
   scenario changed. The pull-request `validate` workflow checks manifests.
4. When published Feature behavior or metadata changes, update that Feature's
   manifest version using SemVer. After integration, the maintainer triggers
   the manual release workflow, whose publish action creates the corresponding
   `feature_<id>_<semver>` tag. Feature README files are generated by that workflow; put
   durable custom notes in `src/<id>/NOTES.md` if needed.
5. Report the files changed and validation results to the maintainer. If the
   Feature layout, validation commands, or release mechanics changed, update
   this skill and its entrypoint pointer in the same change.

Done when the Feature, its relevant tests, and its metadata agree, and the
maintainer has the local validation result needed for integration.
